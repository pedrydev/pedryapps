# AI agents and macOS-native apps

## Question

How do AI agents interact with macOS-native apps, and what are the realistic integration surfaces for exposing the Notifications mini-app so an agent can send notifications in a standard way?

This note focuses on MCP, App Intents, Apple automation mechanisms, security/model boundaries, and architecture options for the Notifications mini-app. It does not select an architecture for the project.

## Scope

- In scope: macOS-only native app, Swift 6, SwiftUI, macOS 14 baseline, one Xcode app target, personal local use, no App Store, sandbox, notarization, login item, or sync ([AGENTS.md](../AGENTS.md)).
- In scope: standard agent-facing protocols and Apple system integration surfaces that can invoke app behavior.
- Out of scope: implementation, iOS/iPadOS/watchOS/tvOS targets, App Store distribution, and a final ADR.
- Research method: primary sources only; claims below are tied to the source that owns them. Unverified items are explicitly listed as gaps.
- No prior research-note convention existed in the repo: `docs/` contains `adr/`, `agents/`, `mini-apps/`, and glossary files, but no `docs/research/` ([AGENTS.md](../AGENTS.md)). This note is therefore placed under `docs/research/` because global non-code artifacts belong under `docs/<kind>/` ([AGENTS.md](../AGENTS.md)).

## Findings by topic (with citations)

### 1. MCP: protocol shape, transports, discovery, SDKs, and security

- MCP is an open standard for connecting AI applications to external systems, data sources, tools, and workflows; the docs describe it as a common integration layer for AI apps and agents ([MCP introduction](https://modelcontextprotocol.io/docs/getting-started/intro)).
- The current MCP docs index lists specification version `2026-07-28` ([MCP docs index](https://modelcontextprotocol.io/llms.txt)).
- MCP uses a host/client/server architecture: a host creates and manages clients, controls permissions and lifecycle, enforces security and consent, handles authorization, coordinates AI/LLM integration, and aggregates context; each client talks to exactly one server ([MCP architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture/index.md)).
- The current architecture is stateless: every request is self-contained and carries its protocol version and capabilities, rather than relying on a negotiated long-lived session ([MCP architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture/index.md), [MCP versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md)). Older MCP architecture docs described stateful sessions, so new design should follow the current version unless compatibility with older clients is required ([2025-06-18 architecture](https://modelcontextprotocol.io/specification/2025-06-18/architecture)).
- MCP is built on JSON-RPC and defines standard transports as bindings that deliver requests, responses, and notifications while preserving the same protocol semantics ([MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/index.md)).
- The two standard transports are stdio and Streamable HTTP; custom transports are allowed if they preserve the required framing and message rules ([MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/index.md)).
- In stdio, the client launches the MCP server as a subprocess; JSON-RPC messages are newline-delimited over stdin/stdout, stderr is for logging, stdout must contain only valid MCP messages, and shutdown is normally initiated by closing the child's input stream ([MCP stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md)).
- The stdio binding also states that the wire format works over Unix domain sockets, TCP connections, or similar reliable bidirectional byte streams, and that custom transports should reuse the same framing and message rules ([MCP stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md)).
- In Streamable HTTP, each message is an HTTP POST to a single MCP endpoint and a response is either a JSON object or a request-scoped SSE stream; the older HTTP+SSE transport from `2024-11-05` was replaced by Streamable HTTP ([MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/index.md), [2025-06-18 transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)).
- Request metadata such as protocol version, per-request capabilities, and optional client identity is carried inline in `_meta.io.modelcontextprotocol/*`; there is no header layer in stdio ([MCP stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md)).
- MCP servers expose capabilities through Tools, Resources, and Prompts: Tools are model-controlled functions, Resources are application-controlled read-only context, and Prompts are user-controlled templates ([MCP server concepts](https://modelcontextprotocol.io/docs/2026-07-28/learn/server-concepts.md)).
- Tools can write to databases, call APIs, modify files, or trigger application logic, and the spec says implementations SHOULD keep a human in the loop with the ability to deny tool calls and SHOULD provide UI indicators and confirmation prompts when tools are invoked ([MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)).
- The docs demonstrate local MCP connection using Claude Desktop as an example client; the concepts are described as broadly applicable to other MCP-compatible clients, and local servers extend AI apps with controlled access to local resources and tools ([Connect local servers](https://modelcontextprotocol.io/docs/2026-07-28/develop/connect-local-servers.md)).
- Claude Code documents MCP as a way to connect to external tools and data sources, where servers give Claude access to tools, databases, and APIs ([Claude Code MCP](https://code.claude.com/docs/en/mcp)).
- No primary source found in this research establishes a generic macOS OS-level service for apps to advertise MCP servers to arbitrary agents. The documented path is client-side configuration/discovery such as Claude Desktop's local-server configuration, or a client connecting to a stdio subprocess or HTTP endpoint ([Connect local servers](https://modelcontextprotocol.io/docs/2026-07-28/develop/connect-local-servers.md), [MCP stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md), [MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/index.md)).
- Official SDKs include TypeScript, Python, C#, Go, Rust, Ruby, Java, Swift, PHP, and Kotlin; the Swift SDK is listed as `modelcontextprotocol/swift-sdk` at Tier 3 ([MCP SDKs](https://modelcontextprotocol.io/docs/2026-07-28/sdk.md)).
- The Swift SDK repository describes itself as the official Swift SDK for MCP servers and clients, maintained in collaboration with Apple ([Swift SDK repository](https://github.com/modelcontextprotocol/swift-sdk)).
- The Swift SDK README says it implements the `2025-11-25` MCP specification, supports macOS 13+, and provides `StdioTransport`, `HTTPClientTransport`, `StatelessHTTPServerTransport`, `StatefulHTTPServerTransport`, `InMemoryTransport`, and `NetworkTransport` ([Swift SDK README](https://raw.githubusercontent.com/modelcontextprotocol/swift-sdk/main/README.md)).
- There is a version caveat: the MCP docs index shows `2026-07-28`, while the Swift SDK README says it implements `2025-11-25`; the spec supports modern per-request metadata and legacy initialize-handshake versions, so compatibility needs verification before relying on SDK behavior for the newest protocol features ([MCP docs index](https://modelcontextprotocol.io/llms.txt), [Swift SDK README](https://raw.githubusercontent.com/modelcontextprotocol/swift-sdk/main/README.md), [MCP versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md)).
- Local MCP servers are ordinary OS processes launched by the host as children of the user account; they inherit environment variables and can read anything the account can read, including keys, credentials, browser profiles, and home-directory data, and can make outbound network connections ([Local server security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security.md)).
- MCP security guidance covers attacks such as confused deputy and emphasizes authorization decisions; Dynamic Client Registration is deprecated as of `2026-07-28` ([Security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices.md)).

### 2. App Intents: Apple-native discovery and invocation

- The App Intents framework makes app actions and data discoverable by Apple Intelligence and system experiences such as Siri, Spotlight, Shortcuts, and widgets; it is available on macOS 13+ ([App Intents framework](https://developer.apple.com/documentation/appintents.md)).
- `AppIntent` expresses app-specific actions for the system; an intent defines `perform()` to execute the action and can declare inputs with `@Parameter` that may be resolved from conversation or explicitly requested ([AppIntent](https://developer.apple.com/documentation/appintents/appintent.md)).
- `AppShortcutsProvider` supplies preconfigured app shortcuts, and Apple docs link WWDC22 sessions 10170 and 10169 for implementing and designing App Shortcuts ([AppShortcutsProvider](https://developer.apple.com/documentation/appintents/appshortcutsprovider.md)).
- App Shortcuts combine an intent with a title, image, spoken phrases, and preconfigured parameters; compiler-generated metadata makes shortcuts available on install ([App Shortcuts](https://developer.apple.com/documentation/AppIntents/app-shortcuts.md)).
- `AppEntity` makes custom app types and concepts discoverable by Apple Intelligence, Siri, and Shortcuts; identifiers must be unique and persistent because the system may save them in shortcuts, and `@Property` members are visible to the system ([AppEntity](https://developer.apple.com/documentation/AppIntents/appentity.md)).
- Apple Intelligence and Siri AI use app intents, entities, and enums to access app actions and content; Apple's guidance includes Spotlight semantic indexing, Transferable/App Intents types for cross-app movement, schemas, onscreen context, and donations ([Apple Intelligence and Siri AI](https://developer.apple.com/documentation/AppIntents/apple-intelligence-and-siri-ai.md)).
- Apple describes a Siri AI Developer Preview in which custom actions and content can be surfaced to Siri, including requests where the app is in the foreground, in a Live Activity, in conversation, or where the user mentions the app for background requests ([Siri AI Developer Preview](https://developer.apple.com/documentation/AppIntents/siri-ai-developer-preview.md)).
- Apple also describes turning custom App Intents into tools Siri can call, adding titles and descriptions, making entities available to Spotlight, and providing onscreen context; it cautions that preview APIs and Siri functionality may change ([Bringing custom actions and content to Siri](https://developer.apple.com/documentation/AppIntents/bringing-custom-actions-and-content-to-siri.md)).
- `ToolIntent` identifies an `AppIntent` that Siri can call while handling a request; Apple's guidance says good candidates are single-sentence actions with fillable parameters, while poor candidates include widget configuration, shortcut steps, and side effects that need explicit user initiation such as ordering or paying ([ToolIntent](https://developer.apple.com/documentation/AppIntents/toolintent.md)).
- `ToolIntent` availability is macOS 27.3+, and the broader system-experience sample using App Intents is marked macOS 27/Xcode 27+, so those newer Siri tool surfaces are not part of a macOS 14 baseline app ([ToolIntent](https://developer.apple.com/documentation/AppIntents/toolintent.md), [Adopting App Intents](https://developer.apple.com/documentation/AppIntents/adopting-app-intents-to-support-system-experiences.md)).
- App Intents are an Apple system integration mechanism for Apple surfaces; MCP is an open client/server protocol for external AI applications and agents ([App Intents framework](https://developer.apple.com/documentation/appintents.md), [MCP architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture/index.md)). They overlap at “expose an action” but do not replace one another: App Intents make actions available to Siri/Shortcuts/Spotlight/Apple Intelligence, while MCP makes tools available to MCP clients.

### 3. Apple automation surfaces and where MCP fits

- `NSAppleEventManager` registers handlers for specific Apple events and dispatches received events to handlers; Cocoa scriptability can also convert Apple events into script command objects using an app's scriptability information ([NSAppleEventManager](https://developer.apple.com/documentation/Foundation/NSAppleEventManager)).
- `NSAppleScriptEnabled` indicates whether AppleScript is enabled for a bundle ([NSAppleScriptEnabled](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppleScriptEnabled.md)).
- An app that uses APIs that send Apple events must provide `NSAppleEventsUsageDescription`; Apple warns that controlling another app through Apple Events can indirectly expose sensitive information ([NSAppleEventsUsageDescription](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppleEventsUsageDescription.md)).
- `NSAppleScript` can load, compile, and execute scripts, but its `executeAppleEvent(_:error:)` method cannot be used to send Apple events to other applications ([NSAppleScript](https://developer.apple.com/documentation/Foundation/NSAppleScript.md)).
- Custom URL schemes let users or other apps trigger an app with context, but Apple describes URL schemes as a potential attack vector: validate all parameters, discard malformed URLs, and limit actions to ones that do not risk user data ([Defining a custom URL scheme](https://developer.apple.com/documentation/Xcode/defining-a-custom-url-scheme-for-your-app.md)).
- XPC provides lightweight interprocess communication; XPC services are helper tools managed on demand by `launchd`, and Apple lists centralizing work, mediating shared resources, working beyond a client's lifecycle, and privilege isolation as benefits ([XPC](https://developer.apple.com/documentation/XPC.md)).
- Automator actions are bundles that perform tasks, workflows are sequences of actions with output passed as input, and the Automator framework supports loading/running actions and workflows ([Automator](https://developer.apple.com/documentation/Automator.md)).
- MCP is not an Apple OS automation primitive; it is a client/server protocol layered over a transport such as stdio, Streamable HTTP, or a custom transport ([MCP architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture/index.md), [MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/index.md)). An MCP server can call into app-specific behavior that is ultimately implemented with Apple APIs such as UserNotifications, App Intents, XPC, or URL handling.

### 4. Security, permissions, and model considerations for a local, non-sandboxed app

- Local notifications require user authorization for alerts, sounds, and badges; the app requests authorization through `UNUserNotificationCenter` ([Asking permission to use notifications](https://developer.apple.com/documentation/UserNotifications/asking-permission-to-use-notifications.md)).
- `UNUserNotificationCenter` is the central object for notification activities such as requesting authorization, declaring categories and actions, scheduling local notifications, handling APNs payloads, and managing delivered notifications; it is available on macOS 10.14+ ([UNUserNotificationCenter](https://developer.apple.com/documentation/UserNotifications/UNUserNotificationCenter.md)).
- Scheduling a local notification involves creating `UNMutableNotificationContent`, specifying delivery conditions with a trigger, creating a `UNNotificationRequest`, and adding it to `UNUserNotificationCenter`; if delivery occurs while the app is not running or in the background, the system interacts with the user, while foreground delivery is handled by the app ([Scheduling a notification locally](https://developer.apple.com/documentation/UserNotifications/scheduling-a-notification-locally-from-your-app.md)).
- App Sandbox restricts access to system resources and user data through entitlements and is required for Mac App Store apps; this project is explicitly non-sandboxed and for personal local use ([App Sandbox](https://developer.apple.com/documentation/Security/app-sandbox.md), [AGENTS.md](../AGENTS.md)).
- MCP tools are model-controlled and can modify state, so MCP's own spec recommends human-in-the-loop confirmation and clear UI indicators for tool invocation ([MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)).
- A local MCP server is not isolated by MCP itself: it is a normal child process of the user account and inherits that account's access and environment ([Local server security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security.md)).
- Apple Events, URL schemes, and XPC each add their own trust boundaries: Apple Events require a usage description and consent-sensitive handling, URL schemes require strict validation, and XPC can be used to separate or centralize privileged work ([NSAppleEventsUsageDescription](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppleEventsUsageDescription.md), [Defining a custom URL scheme](https://developer.apple.com/documentation/Xcode/defining-a-custom-url-scheme-for-your-app.md), [XPC](https://developer.apple.com/documentation/XPC.md)).

## Architecture options for the Notifications mini-app

- **App Intent only**: implement a send-notification action as an `AppIntent` with typed parameters. This is the most native macOS 14-compatible surface for Siri, Spotlight, and Shortcuts, because App Intents are available on macOS 13+ and are designed for those system experiences ([App Intents framework](https://developer.apple.com/documentation/appintents.md), [AppIntent](https://developer.apple.com/documentation/appintents/appintent.md), [AppEntity](https://developer.apple.com/documentation/AppIntents/appentity.md)). Limit: it is not an MCP server and does not make the action available to arbitrary MCP clients; newer Siri tool calling is macOS 27.3+ preview territory, not the macOS 14 baseline ([ToolIntent](https://developer.apple.com/documentation/AppIntents/toolintent.md), [Bringing custom actions and content to Siri](https://developer.apple.com/documentation/AppIntents/bringing-custom-actions-and-content-to-siri.md)).
- **MCP server embedded in the GUI app**: use an in-process/custom transport or a local HTTP endpoint to expose a `send_notification` tool. MCP permits custom transports, and the Swift SDK includes `InMemoryTransport` and HTTP server transports, but stdio specifically assumes the client launches a server subprocess and a GUI app does not naturally provide a clean stdin/stdout channel ([MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/index.md), [MCP stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md), [Swift SDK README](https://raw.githubusercontent.com/modelcontextprotocol/swift-sdk/main/README.md)). Limit: SDK/spec version mismatch needs verification, and adding the Swift SDK is a dependency decision because the project defaults to no third-party dependencies ([MCP SDKs](https://modelcontextprotocol.io/docs/2026-07-28/sdk.md), [Swift SDK README](https://raw.githubusercontent.com/modelcontextprotocol/swift-sdk/main/README.md), [AGENTS.md](../AGENTS.md)).
- **Separate MCP helper plus XPC into the main app**: expose a stdio MCP server from a small helper executable and have it call the main app through XPC to schedule the notification. This matches the stdio lifecycle, keeps protocol traffic off the GUI app's stdio, lets the main app own notification authorization and delivery, and uses Apple's recommended IPC mechanism for helper-to-app work ([MCP stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md), [XPC](https://developer.apple.com/documentation/XPC.md), [UNUserNotificationCenter](https://developer.apple.com/documentation/UserNotifications/UNUserNotificationCenter.md), [Scheduling a notification locally](https://developer.apple.com/documentation/UserNotifications/scheduling-a-notification-locally-from-your-app.md)). Limit: it adds a helper process and an IPC boundary, and the helper still runs with the user's authority under MCP local-server security rules ([Local server security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security.md)).
- **MCP server plus direct UserNotifications from the helper**: simplest for a helper, but notification attribution and authorization behavior need verification because `UNUserNotificationCenter` is app/extension-centric and local notifications are described in terms of an app scheduling them ([UNUserNotificationCenter](https://developer.apple.com/documentation/UserNotifications/UNUserNotificationCenter.md), [Scheduling a notification locally](https://developer.apple.com/documentation/UserNotifications/scheduling-a-notification-locally-from-your-app.md)). This is less attractive if notifications should clearly belong to the main app.
- **URL scheme or Apple Events fallback**: an agent that can open URLs or send Apple events could invoke the app through a custom URL scheme or an Apple event handler. These are existing macOS automation surfaces, but they are not MCP, Apple explicitly warns that URL schemes require validation and low-risk actions, and Apple Events require a usage description and careful consent handling ([Defining a custom URL scheme](https://developer.apple.com/documentation/Xcode/defining-a-custom-url-scheme-for-your-app.md), [NSAppleEventManager](https://developer.apple.com/documentation/Foundation/NSAppleEventManager), [NSAppleEventsUsageDescription](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppleEventsUsageDescription.md)).
- **Shared domain service underneath multiple surfaces**: regardless of agent surface, the notification action can converge on one app-owned service that validates input and calls UserNotifications. This avoids duplicating notification logic between an App Intent, an MCP tool, and URL/Apple event handlers; UserNotifications provides the scheduling API and authorization model ([Scheduling a notification locally](https://developer.apple.com/documentation/UserNotifications/scheduling-a-notification-locally-from-your-app.md), [Asking permission to use notifications](https://developer.apple.com/documentation/UserNotifications/asking-permission-to-use-notifications.md)).
- **Practical fit for the stated goal**: if the goal is Apple-native invocation, App Intents are the smallest standards-based surface on the current macOS 14 target. If the goal is MCP interoperability, the option most consistent with the current MCP stdio lifecycle is a separate helper MCP server that calls into the main app over XPC. If both are wanted, expose both surfaces over the same app-owned notification action; do not treat App Intents and MCP as the same protocol ([MCP stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md), [XPC](https://developer.apple.com/documentation/XPC.md), [App Intents framework](https://developer.apple.com/documentation/appintents.md), [MCP architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture/index.md)).

## Open questions

- Which agent clients must work? Claude Desktop, Claude Code, another MCP client, Shortcuts, or Siri? Client support determines whether stdio, Streamable HTTP, URL schemes, or App Intents are actually useful ([Claude Code MCP](https://code.claude.com/docs/en/mcp), [Connect local servers](https://modelcontextprotocol.io/docs/2026-07-28/develop/connect-local-servers.md)).
- No primary source found for generic macOS OS-level MCP service discovery; only client-side configuration and client-initiated stdio/HTTP connections are documented ([Connect local servers](https://modelcontextprotocol.io/docs/2026-07-28/develop/connect-local-servers.md), [MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/index.md)).
- Should the project accept the official Swift SDK as its first default-excluded third-party dependency, given that it is Tier 3 and its README targets `2025-11-25` while docs show `2026-07-28`? ([MCP SDKs](https://modelcontextprotocol.io/docs/2026-07-28/sdk.md), [Swift SDK README](https://raw.githubusercontent.com/modelcontextprotocol/swift-sdk/main/README.md), [AGENTS.md](../AGENTS.md)).
- What confirmation policy should `send_notification` use? MCP recommends human-in-the-loop confirmation for tools, but a local notification may be treated differently from destructive actions depending on agent trust and user preference ([MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)).
- Does a notification scheduled by a helper get attributed to the helper rather than the main app, and does that matter for this personal-use app? Primary docs describe notification scheduling through `UNUserNotificationCenter` but do not settle this architecture question directly ([UNUserNotificationCenter](https://developer.apple.com/documentation/UserNotifications/UNUserNotificationCenter.md), [Scheduling a notification locally](https://developer.apple.com/documentation/UserNotifications/scheduling-a-notification-locally-from-your-app.md)).
- What tool/input schema should be exposed: title, subtitle, body, delay/trigger, sound, badge, category/actions, and stable identifier? The available fields and triggers are documented by UserNotifications, but the product surface is still a design choice ([Scheduling a notification locally](https://developer.apple.com/documentation/UserNotifications/scheduling-a-notification-locally-from-your-app.md)).
- Should URL schemes or Apple Events be supported at all, given Apple's warnings about URL validation and Apple Events consent? ([Defining a custom URL scheme](https://developer.apple.com/documentation/Xcode/defining-a-custom-url-scheme-for-your-app.md), [NSAppleEventsUsageDescription](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppleEventsUsageDescription.md)).
- Newer Siri AI tool support is preview/newer-OS territory; its suitability for this macOS 14+ app is unresolved ([ToolIntent](https://developer.apple.com/documentation/AppIntents/toolintent.md), [Bringing custom actions and content to Siri](https://developer.apple.com/documentation/AppIntents/bringing-custom-actions-and-content-to-siri.md)).
- Primary-source gap: Apple archive pages for the AppleScript Language Guide and Cocoa Automation Guide returned HTTP 403 during this research (`https://developer.apple.com/library/archive/documentation/AppleScript/Conceptual/AppleScriptLangGuide/introduction/ESLRIntro.html` and `https://developer.apple.com/library/archive/documentation/Automation/Conceptual/CocoaAutomationGuide/AutomatingApplications/AutomatingApplications.html`). Modern Foundation docs were used instead for Apple event handling and scriptability.
- Primary-source gap: WWDC session URLs beyond the 2022 sessions linked from Apple's `AppShortcutsProvider` docs were not verified in this pass ([AppShortcutsProvider](https://developer.apple.com/documentation/appintents/appshortcutsprovider.md)).
